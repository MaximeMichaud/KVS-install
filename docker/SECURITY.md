# Network exposure and origin protection

## Default service exposure

The standard Docker Compose configuration publishes these ports:

| Service | Host binding | Container port |
| --- | --- | --- |
| Nginx, single-site mode | All host addresses, unless `HTTP_PORT` / `HTTPS_PORT` select an address | TCP 80 / 443 |
| MariaDB | `127.0.0.1` | TCP 3306 |
| Memcached or Dragonfly's Memcached interface | `127.0.0.1` | TCP 11211 |
| Manticore, when enabled | `127.0.0.1` | TCP 9306 / 9308 |
| PHP-FPM, Dragonfly's Redis interface, internal Manticore HTTP endpoint | Not published | TCP 9000 / 6379 / 8080 |

In multi-site mode, the primary Nginx has no published ports. Additional sites
do not publish database or cache ports either. Caddy publishes HTTP, HTTPS and
HTTP/3 on ports 80/TCP, 443/TCP and 443/UDP; its administration API stays inside
its container.

The loopback binding is on the **Docker host**. Database and cache services
must remain reachable over their private Docker network by PHP and other
authorized services. Setting MariaDB's internal `bind-address` to `127.0.0.1`
would prevent those containers from connecting. Containers on the same Docker
network can reach each other's listening ports, including unpublished ports.

These are the repository defaults. Compose overrides, other containers, Docker
daemon networking options and host firewall rules can change the result.
Docker documents a localhost-publication limitation for Engine versions before
28.0.0 affecting peers on the same L2 network. See
[Docker port publishing](https://docs.docker.com/engine/network/port-publishing/).

## Requests to the IP address or an unknown domain

New installations reject these requests by default:

- Nginx closes HTTP connections with its `444` behavior. It sends no HTTP status,
  site content or canonical-domain redirect; curl normally reports an empty reply.
- With missing or unknown TLS SNI, Nginx rejects the TLS handshake before
  presenting a site certificate. This requires Nginx 1.19.4 or later.
- A valid SNI with an unknown or missing HTTP Host is also rejected.
- Caddy closes HTTP connections for unmatched domains. It only proxies configured
  site names, and active upstream health checks send the configured Host header.

Configured domain names keep their normal site routing, canonical redirects and
HTTP ACME challenge endpoint. The bare-metal installer also installs default
HTTP and TLS rejection servers.

The Docker entrypoint regenerates the Nginx configuration from the template at
startup. Existing deployments must update the repository and rebuild/recreate
Nginx to use the changed entrypoint and templates. Existing Caddy site files must
also be regenerated by `site-manager.sh` so their active health checks carry the
Host header. Existing additional-site Compose files must also use the updated
Nginx health check from `docker-compose.site.yml.template`, which sends the domain
as Host. Editing only a generated `kvs.conf` is not persistent across recreation.

## Sites behind Cloudflare

Rejecting unknown names prevents a basic IP scan from revealing the site's
domain. It does **not** require requests to come through Cloudflare. A client
that already knows the domain can send the correct Host and TLS SNI directly to
the origin. Nginx `set_real_ip_from` directives only identify trusted forwarding
proxies; they are not an access allowlist.

For an origin that must accept public web traffic only through Cloudflare:

- Restrict inbound web ports to Cloudflare's published IPv4 and IPv6 ranges at
  the provider firewall/security group or at the Docker-aware host firewall.
  Keep the ranges current and scope the rules to web traffic so management
  access and container-to-container traffic remain usable.
- Account for all public endpoints, including Caddy's UDP 443 if enabled, and
  any extra host bindings or load balancers.
- Plan ACME certificate issuance and renewal before restricting traffic.
  HTTP validation must still reach its challenge through the configured route;
  DNS validation is another option.
- Consider Authenticated Origin Pulls with a certificate specific to the zone
  or hostname for origin authentication. Cloudflare's shared AOP certificate
  establishes Cloudflare network membership, not an exclusive account identity.

The installer does not install Cloudflare-only firewall rules automatically:
it also supports sites without Cloudflare and origins behind other proxies.
Docker-published traffic can bypass ordinary UFW `INPUT` rules. The correct
enforcement point depends on Docker's iptables or nftables backend; do not flush
Docker's generated rules. See [Docker firewall behavior](https://docs.docker.com/engine/network/packet-filtering-firewalls/),
[Cloudflare origin IP restrictions](https://developers.cloudflare.com/fundamentals/concepts/cloudflare-ip-addresses/)
and [Authenticated Origin Pulls](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/explanation/).

HTTP rejection and a host firewall do not stop a volumetric attack from filling
the origin's upstream connection. Provider-side filtering and DDoS protection
are needed for that threat. An origin IP may also already be discoverable from
DNS history, other services or past records.

## Verification

From the deployment's `docker` directory, inspect the effective bindings without
printing the database credentials stored in the environment:

```bash
docker compose ps -q | xargs -r docker inspect \
    --format '{{.Name}} {{json .HostConfig.PortBindings}}'
```

Check exposure from a separate machine as well as locally. A bare-IP HTTP request
should close without a redirect; HTTPS with unknown SNI should fail its handshake.
For a Cloudflare-only deployment, a direct connection with the **correct** Host
and SNI must also fail, while requests through Cloudflare and certificate renewals
must continue working.

Repository validation uses synthetic sites and disposable containers:

```bash
bash tests/test_origin_security.sh
bash tests/integration_origin_security.sh
```

The integration test requires local `nginx:alpine` and `caddy:2-alpine` images.
It checks real HTTP/TLS behavior, configured domains, ACME, configuration
regeneration, container restart and Caddy health checks. It does not alter a
running deployment or its host firewall.
